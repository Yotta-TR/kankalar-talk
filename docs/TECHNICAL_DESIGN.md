# التصميم التقني التنفيذي — Kankalar Talk

## 1. الغرض والنطاق

يوثق هذا الملف التصميم التقني التنفيذي لمشروع Kankalar Talk استنادًا إلى [مواصفات المنتج](./PRODUCT_SPEC.md) والقرارات المعتمدة للمشروع. المنتج يستهدف في البداية الناطقين بالعربية الذين يتعلمون التركية. يبدأ نطاق الإصدار الأول بالتعلم النصي والمواقف اليومية للمستويات A1–B1، مع دعم واجهة عربية RTL وتركية LTR. الرسائل الصوتية غير الفورية مرحلة مستقلة تأتي بعد اختبار جودة النسخة النصية، ولا تؤخر إطلاقها. المكالمات الصوتية الحية مرحلة مستقبلية مستقلة تسبقها دراسة جودة وتكلفة وخصوصية.

التصميم موجه لفريق صغير، ويعتمد تطبيقًا خلفيًا واحدًا مقسمًا إلى وحدات واضحة (Modular Monolith)، دون خدمات مصغرة. لا يختار مزودًا للذكاء الاصطناعي أو الصوت، ولا يحسم القرارات التي ما زالت مفتوحة.

## 2. قرارات التنفيذ المعتمدة

- تطبيق الهاتف: Flutter باستخدام Dart، يبدأ على Android مع قابلية دعم iOS لاحقًا.
- الخلفية: NestJS وTypeScript على Node.js 24 LTS.
- المعمارية: Modular Monolith، وليس Microservices.
- الاتصال بين تطبيق الهاتف والخلفية: REST API باستخدام JSON عبر HTTPS.
- توثيق واجهات API: OpenAPI/Swagger.
- قاعدة البيانات الأساسية: PostgreSQL.
- الوصول إلى PostgreSQL: Prisma ORM 7.
- حزم Backend: npm.
- اختبارات Backend: Jest.
- Dialogue Coordinator يعمل داخل الخلفية، وهو المسؤول عن اختيار Eren أو Elif.
- تُدمج محركات الذكاء الاصطناعي والصوت عبر واجهات مستقلة ومحولات قابلة للتبديل.
- لا يتصل تطبيق الهاتف مباشرة بمحركات الذكاء الاصطناعي أو الصوت، ولا يحتوي على مفاتيح خدماتها السرية.
- الإصدار النصي الأساسي مستقل عن الصوت؛ لا تؤخر إضافة الصوت إطلاقه.
- الرسائل الصوتية غير الفورية مرحلة لاحقة للنسخة النصية المختبرة، وتستخدم Object Storage منفصلًا عن PostgreSQL.
- المكالمات الصوتية الحية ليست جزءًا من الإصدار الأول أو شرطًا لإطلاق الرسائل الصوتية؛ تعتمد فقط بعد تقييم مستقل.
- OpenAPI هو العقد الرسمي المشترك بين تطبيق Flutter/Dart والخلفية NestJS/TypeScript.

هذه القرارات تحدد التقنيات الأساسية، ولا تعني اعتماد مكتبة Flutter بعينها لإدارة الحالة أو عميل الشبكة، ولا اختيار مزود استضافة أو مصادقة أو ذكاء اصطناعي أو صوت.

### تنظيم تطبيق Flutter

- تقسيم التطبيق حسب الميزات، بحيث تجمع كل ميزة الواجهات والحالة والوصول إلى البيانات المرتبطة بها.
- `core`: عميل REST موحد، معالجة الأخطاء، إعدادات البيئة، ومكونات مشتركة.
- `l10n`: ترجمة الواجهة واتجاه العرض؛ اتجاه واجهة التطبيق لا يفرض اتجاه كل مقطع نصي تعليمي مختلط اللغة.
- `conversation`: عرض الرسائل، الإرسال، حالات الانتظار والفشل، وإعادة المحاولة الآمنة.
- يمكن لميزة المحادثة عرض رسائل نصية وصوتية في سجل واحد؛ لا تُفعّل واجهات الصوت قبل مرحلتها.
- `learning_path` و`progress`: قراءة بيانات الخادم وعرضها؛ الخادم هو مصدر الحقيقة للتقدم.
- لا يحتوي التطبيق على مفاتيح المحركات، ولا يقرر أي شخصية تتحدث؛ ذلك من مسؤولية الخلفية.
- يمكن إضافة تخزين محلي محدود لاحقًا، بعد تحديد ما يخزن ومدة الاحتفاظ والحماية المناسبة.

### تنظيم Backend

توجد وحدات NestJS في تطبيق واحد. لكل وحدة مسؤولية محددة، مع اعتمادها على واجهات الوحدات الأخرى بدل الوصول العشوائي إلى تفاصيلها الداخلية. تستخدم Prisma للوصول إلى PostgreSQL وإدارة تغييرات المخطط عبر migrations.

## 4. وحدات Backend ومسؤولياتها

| الوحدة | المسؤولية |
|---|---|
| `Auth` | التحقق من الهوية وصلاحية الجلسة. طريقة تسجيل الدخول ومصدر الهوية ما زالا غير محسومين. |
| `Users` | ملف المستخدم وإعداداته الضرورية، مثل لغة الواجهة. |
| `Content` | مستويات CEFR والمسار التعليمي والمواقف ونسخ المحتوى. |
| `Assessment` | إنشاء محاولة تقييم وحفظ نتيجتها وإصدار طريقة التقييم؛ طريقة القياس تحتاج اعتمادًا. |
| `Learning` | تسجيل إكمال الأنشطة وعرض تقدم المتعلم. |
| `Conversations` | جلسات المحادثة والرسائل والتحقق من ملكية الوصول وسياق الدور. |
| `AudioMessages` | استقبال الرسائل الصوتية والتحقق منها وتخزين مراجعها وجدولة المعالجة، عند بدء المرحلة الصوتية. |
| `DialogueCoordinator` | اختيار Eren أو Elif، تكوين طلب الدور، وفرض قواعد مشاركة المتعلم. |
| `AI` | واجهات مستقلة للمحركات ومحولات التكامل والتحقق من المخرجات. |
| `Usage` | تسجيل الاستهلاك وحجز الحدود قبل الاستدعاء وتسويتها بعده وتطبيق الحصص. |
| `Entitlements` | تحديد ما يحق للمستخدم فعله بناءً على استحقاقه؛ لا ينفذ الدفع في الإصدار الأول. |
| `Privacy` | تصدير البيانات وحذفها ومعالجة دورة حياة البيانات. |
| `Health` | فحوص تشغيلية للخدمة والاعتماديات دون كشف معلومات حساسة. |

تُجمع هذه الوحدات في تطبيق NestJS واحد وقاعدة PostgreSQL واحدة. لا يُفصل أي مكوّن إلى خدمة مستقلة إلا إذا ظهرت حاجة تشغيلية أو تنظيمية مثبتة.

## 5. تصميم PostgreSQL الأولي

تستخدم الجداول مفاتيح داخلية، ويمكن اعتماد UUID لمعرّفات السجلات عند التنفيذ. تحفظ البيانات المنظمة في أعمدة واضحة، ويستخدم `JSONB` حيث تدعو الحاجة إلى محتوى مرن، لا بدلًا من تصميم العلاقات الأساسية.

### الجداول والعلاقات

```text
users
 ├── user_preferences
 ├── assessment_results
 ├── learning_progress
 ├── conversation_sessions
 │    ├── messages
 │    └── message_requests
 ├── audio_assets                     # بيانات مرجعية فقط؛ الملفات في Object Storage
 ├── usage_reservations
 ├── usage_events
 └── entitlements ─── plans

cefr_levels
 └── scenarios
      └── scenario_versions
```

| الجدول | الحقول الأولية المقترحة | الغرض |
|---|---|---|
| `users` | `id`, `created_at`, `status`, `deleted_at` | هوية داخلية وحالة الحساب؛ قد تُدار بيانات تسجيل الدخول بنظام الهوية الذي سيعتمد لاحقًا. |
| `user_preferences` | `user_id`, `interface_locale`, `created_at`, `updated_at` | التفضيلات الضرورية مثل لغة الواجهة. |
| `cefr_levels` | `code`, `sort_order` | المستويات A1–C2؛ نطاق الإصدار الأول A1–B1. |
| `scenarios` | `id`, `level_code`, `status` | تعريف الموقف. يجب توفير عشرة مواقف يومية على الأقل موزعة بين A1 وB1. |
| `scenario_versions` | `id`, `scenario_id`, `version`, `content`, `published_at` | نسخ ثابتة للمحتوى حتى تبقى الجلسات والنتائج قابلة للتفسير عند تحديثه. |
| `assessment_results` | `id`, `user_id`, `method_version`, `result`, `created_at` | نتيجة تقييم مرتبطة بإصدار طريقة القياس. |
| `learning_progress` | `user_id`, `scenario_id`, `status`, `completed_at`, `updated_at` | تقدم المتعلم على المواقف؛ تفاصيل احتساب الإكمال تحتاج اعتمادًا تربويًا. |
| `conversation_sessions` | `id`, `user_id`, `scenario_version_id`, `status`, `started_at`, `ended_at` | جلسة مرتبطة بموقف ونسخة محتوى محددة. |
| `messages` | `id`, `session_id`, `sequence_no`, `speaker_type`, `character`, `message_type`, `text`, `transcription_text`, `audio_asset_id`, `reply_to_message_id`, `correction`, `explanation`, `created_at` | سجل موحد للرسائل النصية والصوتية. `message_type` يميز النوع دون تقييد الأنواع المستقبلية؛ `text` و`transcription_text` حقول منفصلة، و`audio_asset_id` مرجع اختياري، لا ملف ثنائي. رد الشخصية يحفظ مستقلًا عن رسالة المستخدم، ويمكن أن يتضمن نصًا وصوتًا. حقلا التصحيح والشرح العربي المنظمان من نوع `JSONB`. |
| `audio_assets` | `id`, `owner_user_id`, `purpose`, `storage_key`, `media_type`, `size_bytes`, `duration_seconds`, `checksum`, `status`, `created_at`, `deleted_at` | بيانات وصفية ومفتاح تخزين داخلي لملف في Object Storage؛ `purpose` يميز تسجيل المستخدم عن صوت رد الشخصية. لا تحفظ البايتات أو رابطًا عامًا دائمًا في PostgreSQL. يربط `messages.audio_asset_id` بالمرجع عند توافره. |
| `message_requests` | `id`, `user_id`, `session_id`, `client_request_id`, `request_hash`, `request_type`, `status`, `processing_stage`, `transcription_status`, `response_audio_status`, `attempt_count`, `next_attempt_at`, `lease_expires_at`, `user_message_id`, `assistant_message_id`, `response_body`, `failure_code`, `failure_response`, `created_at`, `updated_at` | سجل دائم للطلب ونتيجته وحالة معالجته. `status` إحدى `pending` أو `completed` أو `failed`؛ حالات التحويل والصوت الناتج مستقلة لتوضيح الفشل الجزئي. قيد فريد `UNIQUE (user_id, client_request_id)` يمنع التكرار عبر جلسات المستخدم، ويجعل اختلاف الحمولة أو الجلسة للمفتاح نفسه تعارضًا. |
| `usage_reservations` | `id`, `user_id`, `period_key`, `reserved_units`, `status`, `expires_at` | حجز ذري للحصة قبل استدعاء المحرك لمنع تجاوز الحد عند تزامن الطلبات. |
| `usage_events` | `id`, `user_id`, `session_id`, `message_request_id`, `operation_no`, `operation_type`, `engine_key`, `model_key`, `operation_count`, `input_audio_duration_seconds`, `output_audio_duration_seconds`, `units`, `cost_amount`, `currency`, `cost_status`, `cost_basis`, `created_at` | سجل الاستهلاك والتكلفة المقدرة أو المؤكدة لكل عملية. يسجل مدد صوت المستخدم والرد وعمليات التحويل عند انطباقها؛ التكلفة قد تكون غير متاحة. يضمن `UNIQUE (message_request_id, operation_no)` منع تسجيل العملية نفسها مرتين. المعرفات داخلية ولا تختار مزودًا. |
| `plans` | `id`, `code`, `configuration` | تعريف داخلي للحدود والاستحقاقات، لا يعني تفعيل بيع الخطط. |
| `entitlements` | `id`, `user_id`, `plan_id`, `status`, `starts_at`, `ends_at`, `source` | استحقاق المستخدم ومدته ومصدره، مثل تجربة أو منح إداري في MVP. |

### ضوابط تصميم البيانات

- تربط الرسائل بجلسة محادثة، ويخصص لكل رسالة رقم تسلسلي يحفظ ترتيبها.
- يمثل كل من نص المستخدم وتفريغه الكتابي ورد الشخصية رسالة أو حقلًا مستقلًا ومنظمًا؛ لا تدمج محتويات أطراف الحوار في نص واحد.
- ترتبط الملفات الصوتية برسائلها عبر `audio_asset_id` وبيانات `audio_assets` الوصفية؛ تبقى البايتات في Object Storage.
- تُحفظ بيانات `correction` و`explanation` المنظمة على رسالة الشخصية في `JSONB`، ويُعاد الشكل نفسه عند قراءة سجل المحادثة؛ لا تدمج في نص الرسالة ولا تُفقد عند الاسترجاع.
- يُنشأ سجل `message_requests` قبل بدء المعالجة، ويخزن `user_id` و`client_request_id` وبصمة الحمولة وحالتها ومرحلتها ومراجع الرسائل أو نتيجة الفشل.
- يستخدم القيد الفريد `(user_id, client_request_id)` لحسم التزامن ذريًا حتى لو وصل الطلب نفسه من جلستين. الطلب المتكرر بالمفتاح والحمولة نفسيهما لا ينشئ رسائل أو عمليات جديدة؛ أما اختلاف الحمولة أو الجلسة للمفتاح نفسه فيُرفض بـ`409 Conflict`.
- تربط الجلسة بنسخة موقف لا بمحتوى يتغير، كي تبقى النتائج قابلة للتفسير.
- تضاف فهارس لمفاتيح الربط والتواريخ اللازمة لاستعلامات المستخدم والفترة.
- لا تعدل أحداث التكلفة المسواة بصمت؛ تسجل التصحيحات كأحداث عكسية أو تعديلات مدققة.
- لا تخزن ملفات الصوت الثنائية في PostgreSQL، وافصل بيانات الملف ومرجع التخزين عن نصوص الرسائل وسجلات الاستخدام.
- تُحدد سياسة الاحتفاظ بالرسائل قبل التنفيذ؛ لا يعتمد الاحتفاظ الدائم افتراضيًا.
- تستخدم معاملات PostgreSQL لحجز الاستخدام وتسويته بطريقة آمنة عند التزامن.
- تعتمد تغييرات المخطط على Prisma migrations ومراجعة التغييرات قبل تطبيقها على بيئة الإنتاج.

## 6. تصميم REST API

تستخدم الواجهة بادئة إصدار مثل `/v1`، وتتبادل JSON عبر HTTPS، عدا رفع الملف الصوتي الذي يستخدم `multipart/form-data` عبر HTTPS. **OpenAPI هو المرجع الأساسي لعقد التواصل بين Flutter وNestJS**، ويحدد الطلبات والردود والأخطاء. يمكن توليد نماذج Dart من عقد OpenAPI عند الحاجة؛ لا تُشارك أنواع TypeScript مباشرة مع Flutter. أمثلة المسارات التالية أولية، ويجب تثبيت العقد ومراجعته قبل التطبيق. طريقة المصادقة لم تُحسم.

| العملية | مثال مسار | الهدف |
|---|---|---|
| حالة الخدمة | `GET /v1/health` | فحص الخدمة دون كشف تفاصيل حساسة. |
| ملف المستخدم | `GET /v1/me` | عرض الملف والإعدادات الأساسية. |
| إعدادات الواجهة | `PATCH /v1/me/preferences` | تحديث اللغة والتفضيلات المسموح بها. |
| المسار التعليمي | `GET /v1/learning-path` | عرض المستويات والمواقف المتاحة. |
| المواقف | `GET /v1/scenarios?level=A1` | عرض المواقف المنشورة حسب المستوى. |
| تقييم المستوى | `POST /v1/assessments` | إنشاء محاولة تقييم. |
| نتيجة التقييم | `GET /v1/assessments/{id}` | قراءة نتيجة تخص المستخدم الحالي. |
| بدء جلسة | `POST /v1/conversations` | إنشاء جلسة لموقف متاح. |
| قراءة جلسة | `GET /v1/conversations/{id}` | عرض الجلسة ورسائلها المسموح بها. |
| إرسال رسالة | `POST /v1/conversations/{id}/messages` | إرسال رسالة المتعلم وإرجاع رد الشخصية. |
| إرسال رسالة صوتية | `POST /v1/conversations/{id}/audio-messages` | استقبال ملف `multipart/form-data` بعد بدء مرحلة الصوت؛ يتحقق الخادم من الملف ويخزنه ثم يعيد `202 Accepted` ومعرف الطلب لمتابعة المعالجة. |
| حالة طلب الرسالة | `GET /v1/conversations/{id}/message-requests/{clientRequestId}` | استرجاع حالة الطلب أو نتيجته النهائية بعد إرسال أو إعادة إرسال الرسالة. |
| تشغيل ملف صوتي | `POST /v1/messages/{id}/audio-access` | التحقق من ملكية الرسالة وإصدار رابط مؤقت محدود الصلاحية للملف، عند توفره. |
| حذف تسجيل صوتي | `DELETE /v1/messages/{id}/audio` | التحقق من الملكية وبدء حذف الملف ومرجعه؛ تعاد حالة الحذف إذا كان غير متزامن. |
| إنهاء جلسة | `POST /v1/conversations/{id}/close` | إنهاء النشاط وتسجيل الإكمال عند انطباقه. |
| التقدم | `GET /v1/me/progress` | عرض تقدم المستخدم. |
| حدود الاستخدام | `GET /v1/me/usage` | عرض الحد الحالي والاستهلاك والفترة. |
| طلب التصدير | `POST /v1/me/data-export` | بدء أو تقديم طلب تصدير وفق السياسة المعتمدة. |
| طلب الحذف | `DELETE /v1/me` | بدء حذف الحساب وبياناته وفق السياسة المعتمدة. |

OpenAPI هو العقد الرسمي المشترك بين Flutter/Dart وNestJS/TypeScript، ومواصفاته هي المرجع الأساسي لأسماء الحقول وأنواعها والاستجابات والأخطاء. يمكن توليد نماذج Dart وعميل API من المواصفة؛ لا تُشارك أنواع TypeScript مباشرة مع Flutter. تُراجع تغييرات العقد آليًا ضمن CI، وتكون تغييرات الحقول الاختيارية والإضافية متوافقة قدر الإمكان. أي تغيير كاسر يحتاج إصدار API جديدًا أو فترة انتقال موثقة، مع إبقاء العميل والخادم متوافقين خلال التحديث.

### مثال إرسال رسالة

يرسل التطبيق `clientRequestId` إلزاميًا مع نص المتعلم، ولا يرسل اختيار الشخصية أو بيانات المحرك:

```json
{
  "text": "Merhaba, bir kahve istiyorum.",
  "clientRequestId": "unique-request-id"
}
```

يعيد الخادم نتيجة مكتملة تتضمن الرد والتصحيح والشرح في حقول منظمة. مثال توضيحي:

```json
{
  "message": {
    "id": "message-id",
    "speaker": "character",
    "character": "Eren",
    "text": "Güzel! Kahvenizi nasıl istersiniz?",
    "correction": {
      "originalText": "Ben kahve istiyorum.",
      "correctedText": "Ben bir kahve istiyorum.",
      "note": "صياغة أكثر طبيعية لطلب قهوة."
    },
    "explanation": {
      "language": "ar",
      "text": "إضافة كلمة «bir» تجعل طلبك أكثر طبيعية في هذا السياق."
    }
  },
  "usage": {
    "operations": [
      {
        "type": "conversation_generation",
        "count": 1,
        "unit": "operation"
      }
    ],
    "inputAudioDurationSeconds": null,
    "outputAudioDurationSeconds": null,
    "estimatedCost": null,
    "costCurrency": null
  }
}
```

الوحدات في المثال صريحة: `count` عدد عمليات، ومدد الصوت بالثواني، والتكلفة تقديرية وقد تكون غير متاحة (`null`). لا يحدد المثال حصة أو سعرًا. يُحفظ نص التصحيح والشرح وبنيتهما في حقلي `correction` و`explanation` على رسالة الشخصية في PostgreSQL، ويعيد `GET /v1/conversations/{id}` هذه الحقول لكل رسالة كما هي. للرسائل الصوتية، يحتوي الرد على حالة المعالجة والنص والتفريغ والتصحيح والشرح ومرجع تشغيل مؤقت عند توافره. مخطط OpenAPI التفصيلي هو المرجع ولا يدمج عناصر الرسالة المختلفة في نص واحد.

### منع تكرار الطلبات وحالاتها

- `clientRequestId` إلزامي لكل طلب رسالة نصية أو صوتية، وفريد لكل مستخدم وفق `UNIQUE (user_id, client_request_id)`. يحفظ الخادم بصمة تشمل الجلسة ونوع الطلب ومحتواه أو بصمة الملف بعد التحقق منه.
- ينشئ الخادم سجل `pending` ذريًا قبل بدء أي معالجة مكلفة. عند استقبال طلبات متزامنة بالمفتاح نفسه، يفوز سجل واحد فقط؛ تنتظر الطلبات الأخرى نتيجته أو تعيد حالة `pending`، ولا تبدأ معالجة ثانية.
- إذا كان الطلب `completed` وبصمة الحمولة مطابقة، يعيد الخادم النتيجة المحفوظة ومعرّفات الرسائل والتصحيح والشرح وحالات الصوت والاستهلاك دون إنشاء رد أو استدعاء جديد. يعاد استخدام المفتاح بمحتوى أو جلسة مختلفين يرفض بـ`409 Conflict`.
- إذا كان الطلب `pending`، لا يبدأ الخادم معالجة أخرى؛ يعيد `202 Accepted` وحالة الطلب. يستعلم التطبيق عن الحالة، ويستعيد عامل الخلفية الطلبات العالقة وفق آلية lease موثقة دون تكرار الاستدعاء الخارجي مباشرة.
- الحالات العامة هي `pending`, `completed`, `failed`. يحفظ `processing_stage` وعداد المحاولات وحالات التحويل والتوليد الصوتي لتحديد موضع الفشل. الفشل المؤكد قبل إرسال العملية الخارجية يمكن إعادة جدولته بأمان وفق سياسة محدودة؛ أما فشل الشبكة بعد الإرسال وغياب التأكيد فيبقي النتيجة غير مؤكدة ويحتاج مصالحة، لا إعادة عمياء.
- يعيد الطلب المكرر بحالة `failed` الخطأ المحفوظ ولا يعيد المعالجة. يبدأ المستخدم أو التطبيق محاولة جديدة فقط بعد إظهار الفشل، بمعرف `clientRequestId` جديد، ما لم يثبت الخادم أن إعادة المرحلة آمنة ومحمية بمفتاح منع تكرار.
- عند توفر دعم من المحرك الخارجي، يستخدم الخادم مفتاح منع تكرار ثابتًا مشتقًا من الطلب والعملية. عند عدم توفره لا يضمن التصميم تنفيذًا خارجيًا مرة واحدة؛ يسجل العملية كغير مؤكدة ويمنع إعادة الإرسال التلقائية التي قد تضاعف التكلفة. سياسة المصالحة وإعادة المحاولة قرار تشغيلي قبل الإطلاق.
- سجل الطلب وقيود التفرد في `usage_events` يمنعان معالجة نتيجة محفوظة أو تسجيل العملية نفسها مرتين داخل قاعدة البيانات، لكنهما لا يلغيان احتمال تنفيذ خارجي غير مؤكد.

### معايير API

- التحقق من ملكية الجلسة في كل قراءة أو كتابة؛ لا يكفي أن يكون المعرّف صعب التخمين.
- وضع حدود لحجم الرسالة ومعدل الطلبات وعدد الجلسات المتزامنة.
- فرض `clientRequestId` على الرسائل النصية والصوتية، ومنع التكرار الداخلي وفق دورة الحالات أعلاه دون ادعاء ضمان خارجي غير متاح.
- إرجاع أخطاء منظمة ومفهومة، مثل بلوغ الحد أو عدم توفر المحرك، دون كشف تفاصيل داخلية.
- عدم إتاحة تعديل الخطط أو الحدود من تطبيق الهاتف؛ تقتصر هذه العمليات على الخلفية أو أدوات تشغيل مصرح بها.
- جعل OpenAPI العقد الرسمي المرجعي، والتحقق من توافق التغييرات في CI؛ يمكن توليد نماذج Dart والعميل منه، ولا تُشارك أنواع TypeScript مباشرة مع Flutter.

## 7. تصميم Dialogue Coordinator

المنسق خدمة صريحة في الخلفية وصاحب القرار النهائي بشأن من يتحدث في الدور التالي. يعالج كل رسالة جديدة ضمن تدفق مضبوط:

1. يتحقق من المستخدم والجلسة والموقف وحد الاستخدام.
2. يجلب سياقًا محدودًا: نسخة الموقف، المستوى، الرسائل الضرورية، والتقدم ذي الصلة.
3. يختار Eren أو Elif وفق سياق المحادثة واحتياج المتعلم.
4. يبني طلبًا يتضمن هدف الدور وتعليمات الشخصية المنفصلة وشكل المخرجات المتوقع.
5. يستدعي محرك المحادثة عبر الواجهة الداخلية المستقلة.
6. يتحقق من الرد ومن مطابقته للمخطط وشخصية المتحدث المختارة.
7. يحفظ رد الشخصية والاستهلاك ثم يعيد النتيجة المنظمة للتطبيق.

### قواعد الاختيار الأولية

- لا يكون الاختيار عشوائيًا أو بالتناوب وحده؛ يراعي هدف الدور والموقف واحتياج المتعلم.
- يمكن أن يختار المنسق الشخصية الأخرى بعد الدور السابق إذا خدم ذلك التعلم أو التنوع، لا لمجرد فرض التناوب.
- لا يسمح بسلسلة أدوار بين الشخصيتين دون مشاركة المتعلم. في الإصدار الأول، كل استدعاء لرد شخصية ينتج عن رسالة متعلم.
- تعليمات Eren وElif مستقلة وتحفظ بإصدارات قابلة للمراجعة؛ Eren ودود وعملي ومرح باعتدال، وElif دافئة ومرحة ومشجعة بأسلوب مختلف.
- يحدد المنسق الشخصية؛ لا يبدلها المحرك من تلقاء نفسه.
- عند فشل المحرك أو مخالفة المخرجات للمخطط، لا ينشأ رد يبدو ناجحًا. يعاد خطأ مفهوم للعميل ويسجل الحدث التشغيلي دون نص حساس.

### اختبارات نجاح المنسق

- اختيار مناسب للسياق وهدف التعلم.
- عدم وجود ردود متتابعة بين الشخصيتين دون مشاركة المتعلم.
- الحفاظ على اختلاف نبرة الشخصيتين.
- ملاءمة المفردات والشرح للمستوى.
- التعامل الصحيح مع المهلة وفشل المحرك والرد غير المطابق.

## 8. واجهات محركات المحادثة والصوت

تعرّف وحدة `AI` واجهات داخلية (ports) ومحولات تكامل (adapters). لا يعرف المنسق تفاصيل بروتوكول مزود بعينه، ولا يعتمد التطبيق على عقود خاصة بمزود.

تصور واجهة محرك المحادثة:

```text
ConversationEngine.generate(request) -> structured response
```

يتضمن الطلب ما يلزم فقط: اللغة، المستوى، الموقف، الشخصية وتعليماتها، سياقًا محدودًا، ونمط التصحيح. ويكون الرد وفق مخطط داخلي متفق عليه يتضمن النص التركي، وتصحيحًا اختياريًا، وشرحًا عربيًا اختياريًا.

واجهات الصوت المستقبلية مستقلة عن التطبيق ومزود الخدمة:

```text
SpeechRecognition.transcribe(audio reference, language) -> transcription result
SpeechSynthesis.synthesize(text, character voice profile) -> audio reference
```

التواقيع الفعلية تعتمد على تجربة الصوت. لا يتصل الهاتف بمحرك الصوت مباشرة، ولا تخزن ملفات الصوت في PostgreSQL. تختلف إعدادات الصوت لـEren عن Elif، وتضبط الخلفية ملف صوت كل شخصية بصورة مستقلة عن المزود. تفاصيل الأصوات المتاحة قرار مفتوح للتحقق من الجودة والحقوق والتكلفة.

### الرسائل الصوتية غير الفورية

هذه مرحلة مستقلة تأتي بعد اكتمال النسخة النصية الأساسية واختبار جودتها، ولا تؤخر إطلاقها. وهي رسائل مسجلة وردود صوتية غير متزامنة، وليست مكالمة حية.

1. يسجل المستخدم رسالة ويرسلها من Flutter مع `clientRequestId`.
2. يستقبل الخادم الملف كتدفق `multipart/form-data`، ويتحقق من حد الحجم أثناء الاستقبال، ومن النوع الفعلي عبر ترويسة الملف ومحتواه، ومن المدة بعد فك بيانات الملف. الحدود قابلة للتعديل من إعدادات الخادم، ولا يثق الخادم بقيم يرسلها التطبيق.
3. يخزن الخادم الملف في مساحة Object Storage خاصة، بعد التحقق، ويحفظ في PostgreSQL البيانات الوصفية والمرجع الداخلي فقط. لا يخزن ملفًا ثنائيًا أو رابطًا عامًا دائمًا في قاعدة البيانات.
4. يسجل الخادم طلب المعالجة كـ`pending` بمرحلة `uploaded`، ثم يعالج العامل الطلبات المستديمة داخل بنية الخلفية الحالية. يمكن للعامل استخدام قفل صف/lease في PostgreSQL لاسترداد العمل بعد التعطل؛ لا يتطلب ذلك خدمة مصغرة مستقلة.
5. يحول الخادم الصوت إلى نص عند الحاجة لفهم الرسالة، ويحفظ التفريغ في حقل منفصل عن الملف وعن نص الرسالة. يخضع الاحتفاظ بالتفريغ لسياسة البيانات المعتمدة.
6. يمرر النص والسياق التعليمي إلى Dialogue Coordinator ليختار Eren أو Elif وفق الدور وهدف الموقف.
7. ينشأ رد نصي من الشخصية المختارة، ويحفظ كرسالة منفصلة مع هوية الشخصية والتصحيح اللغوي والشرح العربي الاختياريين.
8. يمكن إنشاء نسخة صوتية للرد من ملف الصوت الخاص بالشخصية. فشل إنشاء الصوت لا يمحو الرد النصي المكتمل؛ تعاد الرسالة بالنص مع حالة صوت فاشل أو غير متاح، وتخضع إعادة المحاولة لمنع التكرار الخارجي.
9. يستقبل التطبيق حالة المعالجة والرد، ويعرض اختياريًا نص المستخدم والتفريغ ورد الشخصية والتصحيح والشرح العربي، ويوفر تشغيل الرسالة والرد وإعادة تشغيلهما.

يعرض API حالات واضحة مثل `pending`, `completed`, `failed` على مستوى الطلب، وحالة مستقلة للصوت الناتج عند اكتمال النص مع تعذر الصوت. لا يعتبر فشل رفع الملف أو التحقق منه طلبًا مكتملًا، وتزال الملفات المؤقتة أو اليتيمة بأمان. فشل التخزين أو التفريغ أو توليد الرد يسجل برمز خطأ آمن، ويعرض التطبيق إجراءً مناسبًا دون ادعاء نجاح. تحدد سياسة إعادة المحاولة بحسب المرحلة ونتيجة العملية الخارجية؛ لا يعاد استدعاء غير مؤكد تلقائيًا.

شكل الاستجابة يفصل عناصر المحادثة ولا يدمجها في نص واحد، مثل:

```json
{
  "clientRequestId": "unique-request-id",
  "status": "completed",
  "userMessage": {
    "id": "user-message-id",
    "messageType": "audio",
    "text": null,
    "transcriptionText": "Merhaba, bir kahve istiyorum.",
    "audioAssetId": "user-audio-asset-id"
  },
  "assistantMessage": {
    "id": "assistant-message-id",
    "messageType": "audio",
    "character": "Elif",
    "text": "Güzel! Kahvenizi nasıl istersiniz?",
    "transcriptionText": null,
    "correction": null,
    "explanation": null,
    "audioAssetId": "assistant-audio-asset-id",
    "audioStatus": "ready"
  },
  "usage": {
    "inputAudioDurationSeconds": 8.6,
    "outputAudioDurationSeconds": 3.2,
    "transcriptionOperations": 1,
    "speechSynthesisOperations": 1,
    "estimatedCost": null,
    "costCurrency": null
  }
}
```

هذه القيم مثال شكل لا حصة أو سعر. تكون مراجع الملفات معرّفات داخلية؛ يطلب التطبيق رابط تشغيل مؤقتًا عبر API بعد تحقق الملكية، ولا يحصل على مفتاح تخزين دائم.

| حالة الفشل | السلوك المطلوب |
|---|---|
| نوع أو حجم أو مدة غير مقبولة | رفض الطلب قبل المعالجة، حذف أي ملف مرحلي، وإرجاع خطأ تحقق واضح. |
| انقطاع الرفع أو فشل التخزين | عدم إنشاء رسالة مكتملة؛ إزالة الملف الجزئي أو تمييزه للتنظيف وإتاحة إعادة إرسال آمنة. |
| فشل التفريغ أو إنشاء رد نصي | حفظ حالة `failed` ورمز آمن؛ عدم عرض نتيجة مختلقة، وإعادة المحاولة فقط وفق حالة العملية الخارجية ومفتاح منع التكرار المتاح. |
| فشل توليد صوت الرد بعد نجاح النص | إبقاء الطلب والرد النصي `completed`، وتعيين `response_audio_status` إلى `failed`، مع إتاحة النص دون ادعاء وجود صوت. |
| نتيجة خارجية غير مؤكدة بعد انقطاع الاتصال | إبقاءها قيد المصالحة وعدم إعادة الإرسال تلقائيًا إذا كان ذلك قد يكرر العملية أو التكلفة. |

لا يسمح بتشغيل ملف إلا بعد التحقق من ملكية الرسالة. يصدر الخادم رابط وصول مؤقتًا وآمنًا عند الحاجة، محدود الصلاحية وفق إعداد قابل للتعديل، وتبقى مساحة التخزين خاصة. يجب دعم إلغاء الوصول والحذف؛ لا يحدد هذا التصميم مدة الرابط أو مدة الاحتفاظ قبل دراسة القرار.

### المكالمات الصوتية الحية

المكالمات الحية مرحلة مستقلة ومتقدمة بعد الرسائل الصوتية، وليست جزءًا من الإصدار الأول أو شرطًا لإطلاق الرسائل النصية أو الصوتية غير الفورية. تحتاج دراسة مستقلة لجودة الحوار والزمن والتكلفة والخصوصية وإدارة المقاطعة والبنية والاتصال، قبل اعتماد حل أو مزود.

### ضوابط قابلية الاستبدال

- محول مستقل لكل تكامل، مع إعدادات وأسرار على الخادم لا في تطبيق الهاتف.
- نموذج داخلي موحد للطلبات والنتائج والأخطاء لا يكشف أسماء حقول خاصة بالمحرك للتطبيق.
- استخدام محرك وهمي في الاختبارات المحلية والآلية.
- اختبارات عقد لكل محول تغطي النجاح والمهلة والرفض والحصة غير المتاحة والرد غير الصالح.
- الاحتفاظ بمعرفات داخلية لقياس التكلفة دون جعل اسم مزود بعينه جزءًا من عقد التطبيق.
- عدم إضافة خدمات تشغيل منفصلة إلا عند وجود حاجة مثبتة.

## 9. إدارة المستخدمين والجلسات والرسائل والتقدم

- الخادم هو مصدر الحقيقة لهوية المستخدم وملكية المحادثات والتقدم.
- تبدأ الجلسة مرتبطة بموقف ونسخة محتوى محددة ومستوى مناسب.
- كل رسالة متعلم نصية أو صوتية تسبب دورة تنسيق واحدة؛ في الصوت، يستخدم المنسق التفريغ عند الحاجة. يمكن أن يضم رد الشخصية تصحيحًا أو شرحًا عند الحاجة.
- تحفظ رسالة المستخدم، وتفريغها، ورد الشخصية، وهوية Eren أو Elif، والتصحيح، والشرح العربي، ومرجع الصوت وحالات المعالجة والاستهلاك كعناصر منفصلة ومنظمة.
- يسجل التقدم نتيجة نشاط قابلة للتفسير، لا مجرد عدد الرسائل. تعريف الإكمال ومؤشراته قرار تربوي مفتوح.
- لا تستخدم المحادثات لأغراض تحليلية ثانوية دون غرض معلن وسياسة معتمدة.
- لا تحتفظ بالتسجيلات الصوتية إلى الأبد. يجب اعتماد مدة احتفاظ وحذف واضحة قبل إطلاق الرسائل الصوتية، ولا تخزن الصوت أطول من الحاجة التشغيلية دون أساس واضح وموافقة مناسبة.
- تتيح الواجهة للمستخدم التحكم بتسجيلاته وطلب حذفها. يتحقق الخادم من الملكية قبل القراءة أو الحذف، ويزيل الملف من Object Storage ومرجعه وفق دورة حذف قابلة لإعادة المحاولة والتدقيق.
- تحمى الملفات أثناء النقل والتخزين، وتقيد صلاحياتها، وتستخدم روابط وصول مؤقتة وآمنة عند الحاجة. لا تسجل محتويات الملفات أو روابطها في سجلات التشغيل.
- تخزن PostgreSQL بيانات الملف الوصفية ومفتاح Object Storage المرجعي فقط، لا البيانات الثنائية. تبقى بيانات مراجع التخزين منفصلة عن نصوص الرسائل وسجلات قاعدة البيانات العامة.
- تظل مدة الاحتفاظ بالتسجيلات، وتفاصيل موافقة المستخدم أو ولي الأمر، ومصير التسجيلات والتفريغات في النسخ الاحتياطية قرارات مفتوحة؛ لا يعتمد المستند مدة أو آلية موافقة نهائية.
- تغطي سياسة الحذف البيانات والسجلات والنسخ الاحتياطية بحسب ما سيُعتمد؛ الحذف من جدول وحده لا يضمن محو النسخ الاحتياطية فورًا.
- تتبع التقييمات إصدار طريقة التقييم كي يمكن تفسير النتائج عند تغير الطريقة.

## 10. حدود الاستخدام والميزانية والتكاليف

### قيود التكلفة والاشتراك

**19 دولارًا هو السعر الشهري المستهدف تجاريًا، وليس سعرًا مثبتًا أو وعدًا باستخدام غير محدود. لن تُحدد حدود الاستخدام الفعلية قبل قياس التكلفة.** لا يمكن استنتاج ربحية هذا السعر من اختيار إطار Backend أو قاعدة البيانات؛ يلزم جمع بيانات استخدام وتكلفة فعلية أو تقديرات موثقة، ثم مراجعتها قبل اعتماد الحصص.

يجب أن تسمح البنية بتعديل حدود الاستخدام من الخادم دون إصدار جديد لتطبيق الهاتف، وتسجيل التكلفة لكل مستخدم بالقدر الممكن، ودعم استحقاقات وخطط قابلة للتوسع دون تفعيل الدفع في الإصدار الأول. لا يُعرض حد ثابت أو وعد استخدام نهائي قبل اعتماد سياسة التكلفة.

### سجل الاستخدام

يسجل الخادم لكل عملية مرتبطة بطلب المستخدم، متى توافرت البيانات، ويتيح نسبتها إلى الحساب والخطة أو الاستحقاق:

- المستخدم والخطة والجلسة والرسالة والطلب المرتبطة.
- نوع العملية وعددها بوحدة معلنة، مثل `operation`، ومعرف المحرك/النموذج الداخلي.
- مدة صوت المستخدم ومدة الصوت الناتج عن رد الشخصية بالثواني، عند انطباقهما.
- عدد عمليات تحويل الكلام إلى نص وتوليد الصوت.
- وحدات الاستخدام الفعلية التي تعيدها الخدمة، مع الوحدة الصريحة.
- تكلفة مقدرة أو فعلية لكل عملية عند توافر بياناتها، والعملة، ونسخة أساس التسعير الداخلي.
- الحالة: محجوز، مكتمل، فشل، أو تسوية متأخرة.

يجب الفصل بين التكلفة التقديرية والتكلفة الفعلية؛ قد لا تتوفر بيانات التكلفة أو قد تتغير، وعند غيابها تسجل القيمة كغير متاحة لا كصفر. لا تعرض للمستخدم دقة مالية غير مضمونة. تكون الحدود والحصص قابلة للتعديل من إعدادات الخادم دون تحديث التطبيق، وتطبق على المستخدم وفق خطته أو استحقاقه. لا يعتمد التصميم استخدامًا غير محدود أو أسعارًا أو حصة ثابتة؛ تتحدد وحدات الحصة وقيمها بعد قياس التكلفة الفعلية.

### دورة الحد

1. يقرأ الخادم حدود الفترة وحدود الصوت، بما يشمل حجم الملف ومدته وعدد العمليات، من إعدادات قابلة للتغيير على الخادم.
2. يحجز الاستهلاك المتوقع أو المعروف بأفضل وحدة متاحة بصورة ذرية في PostgreSQL قبل العمليات المكلفة، لمنع تجاوز الحصص بسبب الطلبات المتزامنة.
3. إذا لم تتوفر حصة، يرفض الطلب دون استدعاء المحرك ويرسل خطأ مفهومًا.
4. بعد الرد، يسوي الحصة وفق قياس الاستهلاك؛ وتُعاد الحصة غير المستخدمة بحسب سياسة تعتمد لاحقًا.
5. يسجل تكلفة أو تقديرًا مرتبطًا بالمستخدم ويتيح قياسًا تشغيليًا مجمعًا.
6. يطبق الخادم حدودًا إضافية على معدل الطلبات وطول الرسالة وحجم السياق وعدد الجلسات المتزامنة.

يجب حفظ نسخة إعداد الحد المطبق مع سجل الطلب لتفسير سلوك النظام تاريخيًا. الوحدة النهائية للحصص الصوتية والنصية ما زالت مفتوحة؛ قد تعتمد على عدد العمليات أو مدد الصوت أو وحدات المحرك أو مزيج، لكن لا تُعتمد قيمة أو تسعيرة قبل معرفة قياسات الاستخدام والتكلفة.

### الحد من الإساءة

- تحديد معدل لكل مستخدم وجلسة، وربما عنوان شبكة وفق سياسة تراعي الخصوصية.
- سقف لطول الرسالة والسياق وعدد الجلسات المتزامنة.
- منع تكرار الطلبات لتفادي استدعاء مدفوع مكرر عند إعادة المحاولة.
- قيود مناسبة للحسابات عند ظهور إساءة استخدام، مع عدم جمع بيانات أكثر مما يلزم.
- استجابة مفهومة عند بلوغ الحد تتضمن فترة إعادة التعيين بعد اعتمادها.
- مراقبة ارتفاع الاستخدام والتكلفة وإعداد تنبيهات تشغيلية عند اعتماد منصة المراقبة.
- استخدام PostgreSQL للحجز في MVP؛ لا تضاف Redis أو خدمة طوابير دون حاجة مثبتة.

## 11. الاشتراكات والاستحقاقات دون تفعيل الدفع

يفصل النظام بين:

- **Plan:** تعريف داخلي لما تتضمنه الخطة من حدود واستحقاقات.
- **Entitlement:** ما يحق لمستخدم معين استخدامه وفي أي فترة.

لا توجد في الإصدار الأول معالجة دفع أو تحصيل أموال أو تكامل مع متاجر التطبيقات. يمكن إنشاء استحقاقات تجريبية أو يدوية للاختبار، مع توضيح مصدرها. تستعلم الوحدات عن استحقاق، مثل القدرة على بدء جلسة، بدل فحص اسم خطة ثابت في كل مسار.

يسمح ذلك بإضافة مصدر دفع لاحقًا لتحديث الاستحقاقات دون ربط منطق المحادثات بمنصة الدفع. تفاصيل الخطط والأسعار الفعلية والفترة التجريبية والإلغاء والاسترداد والضرائب والأسواق تبقى قرارات تجارية مفتوحة. يظل مبلغ 19 دولارًا هدفًا شهريًا فقط إلى أن تُعتمد خطة تجارية وتُثبت استدامة التكلفة.

## 12. الخصوصية والأمان وحذف البيانات

- **تقليل البيانات:** اجمع البيانات اللازمة للتعلم والتشغيل والقياس المعتمد فقط.
- **الهوية والصلاحيات:** تحقق من الهوية وملكية كل مورد في الخلفية، وطبق مبدأ أقل صلاحية على قاعدة البيانات والخدمات.
- **الأسرار:** خزّن أسرار التكامل في بيئة الخادم أو مخزن أسرار منصة الاستضافة عند اختيارها، مع دعم تدويرها. لا تضعها في التطبيق أو المستودع أو سجلات CI.
- **النقل والتخزين:** HTTPS أثناء النقل، وصلاحيات وصول محدودة لقاعدة البيانات والنسخ الاحتياطية. تفاصيل التشفير عند التخزين وإدارة المفاتيح تعتمد على اختيار الاستضافة.
- **المحادثات والسجلات:** لا تسجل نص المحادثة في سجلات التشغيل افتراضيًا، واخفِ البيانات الحساسة من بيانات الرصد.
- **الحذف:** وفر مسارًا موثقًا لحذف الحساب والرسائل والتقدم والبيانات التابعة. حدد مدة انعكاس الحذف على النسخ الاحتياطية قبل الإطلاق.
- **التحكم والتصدير:** صمم واجهات للتحكم بالبيانات والتصدير والحذف، بعد الاتفاق على النطاق وتجربة المستخدم.
- **الحماية التشغيلية:** تحقق من المدخلات، وطبق حدود المعدل والمهلات، ولا تكشف الأخطاء أسرارًا أو تفاصيل داخلية.
- **الامتثال:** تحديد متطلبات الخصوصية ومكان معالجة البيانات والاحتفاظ بها قرار مطلوب قبل الإطلاق التجاري في الأسواق المستهدفة، ولا يفترضه هذا التصميم.

## 13. الاختبارات وCI/CD والنشر ومراقبة الأخطاء

### الاختبارات

1. **اختبارات وحدات Backend باستخدام Jest:** منسق الحوار، قواعد الحصص والحجز والتسوية، الصلاحيات، وحساب التقدم.
2. **اختبارات عقود API:** صحة الطلبات والردود والأخطاء وتوافق Flutter مع عقد OpenAPI المعتمد والمتحقق منه في CI، بما يشمل الرسائل الصوتية وحالات المعالجة والحقول المنظمة.
3. **اختبارات PostgreSQL والتكامل:** Prisma migrations، قيود العلاقات، التزامن في حجوزات الاستخدام، والحذف.
4. **اختبارات محولات المحركات:** محرك وهمي في الاختبارات، وتغطية المهلة والرد غير الصالح. لا تشغّل اختبارات تكامل حقيقية بتكلفة غير مضبوطة.
5. **اختبارات Flutter:** الوحدات والواجهات والتنقل والأخطاء، ودعم العربية RTL والتركية LTR والنص المختلط.
6. **اختبارات تدفق كامل:** بدء موقف نصي وإرسال رسالة واستلام الرد وحفظ التقدم وبلوغ الحد وحذف البيانات؛ اختبار تكرار `clientRequestId` للمستخدم نفسه، وتعارض الحمولة، والطلبات المتزامنة، واسترجاع `pending` و`completed` و`failed` دون تكرار داخلي. تختبر النتيجة الخارجية غير المؤكدة دون ادعاء تنفيذ مرة واحدة.
7. **اختبارات أمنية:** ملكية الجلسة والملفات، الوصول غير المصرح به، التحقق من المدخلات، حدود المعدل، انتهاء صلاحية روابط الوصول، الحذف، وتسرب الأسرار.
8. **اختبارات جودة تعليمية:** مراجعة بشرية وعينات تقييم للطف التصحيح وصحة الشرح العربي وملاءمة CEFR واختلاف Eren وElif.
9. **اختبارات الرسائل الصوتية في مرحلتها فقط:** رفض الأنواع والأحجام والمدد غير المسموحة وفق إعدادات الخادم، رفع فاشل أو مكرر، استعادة المعالجة، تعطل التخزين أو التفريغ أو توليد الصوت، تشغيل الملف وإعادة تشغيله، الحذف، والجودة والتكلفة والخصوصية على أجهزة فعلية.
10. **اختبارات المكالمات الحية مستقبلًا:** تقييم منفصل للصوت والزمن والمقاطعة والشبكات والتكلفة والخصوصية قبل قرار اعتمادها.

### CI/CD والنشر

مسار مقترح تدريجي، على أن تُختار منصة CI/CD لاحقًا:

- عند كل طلب دمج: تنسيق الكود، التحليل الثابت وفحص الأنواع، اختبارات وحدات Jest، وفحص عدم تسرب الأسرار.
- التحقق من مواصفة OpenAPI والتغييرات الكاسرة، وتوليد أو فحص توافق عميل Dart عند اعتماده.
- تشغيل اختبارات التكامل على PostgreSQL معزول واختبار Prisma migrations.
- بناء Backend وتطبيق Android بطريقة قابلة للتكرار.
- نشر نسخة اختبار أولًا والتحقق يدويًا من تدفق تعلم رئيسي واتجاهات اللغات.
- الترقية إلى الإنتاج بموافقة ومراجعة، مع خطة رجوع للنسخة السابقة.
- تنفيذ تغييرات قاعدة البيانات بأسلوب متوافق مع النسخة المنشورة؛ لا تحذف أعمدة مستخدمة في نفس إصدار التطبيق.
- إدارة حزم Backend عبر npm، وتثبيت إصدارات الاعتماديات وإعادة البناء من ملف القفل المعتمد.

### مراقبة الأخطاء والتكلفة

راقب زمن الاستجابة ومعدل الفشل وزمن استدعاء المحرك واستهلاك الحدود والتكلفة المقدرة لكل مستخدم. استخدم معرف طلب لتتبع الأعطال بين API وPostgreSQL والمحرك، دون إدراج نص الرسالة أو بيانات شخصية في السجلات. اختيار منصة الاستضافة وCI والرصد غير محسوم.

## 14. مراحل التنفيذ ومعايير النجاح

كل مرحلة لها مراجعة وموافقة قبل الانتقال إلى المرحلة الكبرى التالية. يمكن إطلاق النسخة النصية بعد اجتياز المرحلة 7؛ لا يشترط تنفيذ الرسائل الصوتية أو المكالمات الحية لذلك.

### المرحلة 1 — تثبيت القرارات والتصميم

**المخرجات:** اعتماد نطاق الإصدار النصي، والهوية، وسياسة بياناته، وتعريف التقدم، وحدود المسؤوليات، وعقد OpenAPI الأولي. تسجيل مدة احتفاظ الصوت والموافقة وحدوده التشغيلية كقرارات مفتوحة إلى ما قبل تنفيذ المرحلة الصوتية.
**معيار النجاح:** مراجعة التصميم وتحديد القرارات المعتمدة والمفتوحة دون افتراض مزود أو سعر أو حصة.

### المرحلة 2 — تأسيس المشروع والبنية الأساسية

**المخرجات:** هيكل Flutter وNestJS، Node.js 24 LTS، npm، Prisma وPostgreSQL، OpenAPI، Jest، وفحوص CI أولية.
**معيار النجاح:** يمكن تشغيل الاختبارات والبناء وفق خطوات موثقة، ويجتاز العقد التحقق الآلي دون أسرار فعلية.

### المرحلة 3 — الحسابات والمستخدمون والمحتوى

**المخرجات:** طريقة هوية معتمدة، إعدادات المستخدم، المستويات والمواقف وإصدارات المحتوى ومسارات API.
**معيار النجاح:** يرى المستخدم المخول المواقف المنشورة المناسبة، ويرفض الخادم الوصول غير المصرح به؛ يتوفر محتوى موزع على A1–B1 وفق المواصفات.

### المرحلة 4 — المحادثة النصية باستخدام محرك تجريبي

**المخرجات:** جلسات ورسائل نصية عبر REST، Dialogue Coordinator، واجهة محرك وهمي، وواجهة Flutter أولية.
**معيار النجاح:** إكمال موقف نصي كامل بالمحرك التجريبي، واختبار اختيار Eren أو Elif، مشاركة المتعلم، الأخطاء، وidempotency دون اتصال خارجي مدفوع.

### المرحلة 5 — دمج محرك المحادثة وقياس الجودة والتكلفة

**المخرجات:** محول خلفي قابل للاستبدال، تقييم جودة تعليمية، وقياس الاستهلاك والتكلفة مع حدود قابلة للتعديل من الخادم.
**معيار النجاح:** اجتياز معايير جودة موثقة وفهم التكلفة الفعلية أو حدود تقديرها؛ لا يختار مزود قبل موافقة منفصلة على الجودة والتكلفة والخصوصية.

### المرحلة 6 — التقييم والتقدم والخصوصية

**المخرجات:** طريقة تقييم معتمدة، عرض تقدم، والتحكم والتصدير والحذف وفق سياسة البيانات.
**معيار النجاح:** نتائج قابلة للتفسير وإمكانية اختبار الحذف والبيانات التابعة والنسخ الاحتياطية وفق سياسة معلنة.

### المرحلة 7 — الاختبار التجريبي للنسخة النصية

**المخرجات:** اختبار تنقل وأخطاء وشبكة وأمان وجودة تعليمية على أجهزة فعلية، وإطلاق تجريبي محدود للنسخة النصية.
**معيار النجاح:** تدفق النص كامل ومستقر، الاستخدام والتكلفة قابلان للقياس، ولا توجد مشكلة حرجة مفتوحة تمنع إطلاق النسخة النصية. لا تؤجلها أعمال الصوت.

### المرحلة 8 — تصميم وتنفيذ الرسائل الصوتية غير الفورية

**المخرجات:** اعتماد سياسة الاحتفاظ والموافقة والحدود القابلة للتعديل؛ استقبال وتحقق وتخزين خاص في Object Storage؛ معالجة التفريغ والرد النصي والصوت الاختياري بصوتين مميزين؛ دعم حالة المعالجة وإعادة التشغيل والحذف؛ وتحديث OpenAPI ومخطط البيانات.
**معيار النجاح:** يعمل تدفق رسالة المستخدم ورد Eren أو Elif دون تخزين ملفات في PostgreSQL، ويمكن عرض التفريغ والتصحيح والشرح العربي اختياريًا، مع معالجة الفشل ومنع التكرار.

### المرحلة 9 — اختبار جودة الصوت والتكلفة والخصوصية

**المخرجات:** اختبارات على أجهزة فعلية وشبكات مختلفة لرفع الملفات والتحويل وتوليد الصوت والروابط المؤقتة والحذف، وقياس الاستهلاك والتكلفة والاحتفاظ.
**معيار النجاح:** اعتماد جودة وتجربة وحدود تكلفة وسياسة خصوصية موثقة قبل إتاحة الميزة للمستخدمين؛ لا يفترض استخدام أو سعر غير محدود.

### المرحلة 10 — دراسة المكالمات الصوتية الحية

**المخرجات:** تقييم مستقل للجودة والزمن والتكلفة والخصوصية والمقاطعة وتناوب المستخدم مع شخصية واحدة أو الشخصيتين والبنية التشغيلية.
**معيار النجاح:** قرار منفصل بالمضي أو التأجيل بناءً على تجربة وقياسات ومراجعة أمن وخصوصية؛ لا تكون المكالمات شرطًا لأي إصدار سابق.

## 15. القرارات المفتوحة

لا تحسم هذه الوثيقة الخيارات التالية:

1. طريقة التسجيل والمصادقة، وهل يلزم الحساب قبل أول درس.
2. سياسة تخزين المحادثات ومدة الاحتفاظ والتصدير والحذف وتأثير النسخ الاحتياطية.
3. وحدة حد الاستخدام الفعلية، وحدودها، وموعد إعادة ضبطها وطريقة عرضها للمستخدم.
4. تعريف التقدم واحتساب إكمال المواقف، وطريقة تقييم المستوى ودقتها.
5. التوزيع التفصيلي للمواقف العشرة أو أكثر بين A1 وB1 ومراجعتها التربوية.
6. شروط اعتماد الرسائل الصوتية لاحقًا من حيث الجودة والتكلفة والخصوصية، وحدود نوع الملف وحجمه ومدته القابلة للتعديل.
7. مزودو الذكاء الاصطناعي والصوت؛ لا يُختار أي منهم في هذا التصميم.
8. منصة استضافة Backend وقاعدة البيانات ومكان البيانات، ومنصة CI/CD والرصد وإدارة الأسرار.
9. التشفير عند التخزين وإدارة المفاتيح بحسب الاستضافة المعتمدة.
10. شكل الخطط التجارية الفعلية، والأسواق والضرائب والإلغاء والاسترداد؛ مبلغ 19 دولارًا هدف شهري وليس تفعيلًا للدفع.
11. سياسة مدة الاحتفاظ بالتسجيلات والتفريغات، وآلية الموافقة المناسبة للمستخدمين والأطفال، وكيفية تطبيق الحذف على النسخ الاحتياطية.
12. مدة صلاحية رابط تشغيل الصوت، ومدة الاحتفاظ بالملفات المؤقتة، وآلية إعادة المحاولة أو المصالحة للعمليات الخارجية غير المؤكدة.
13. مكتبات Flutter لإدارة الحالة والشبكة والتخزين المحلي، إذ لم تُعتمد ضمن القرارات الحالية.

## 16. التوصية التنفيذية

نفّذوا التصميم على مراحل صغيرة قابلة للمراجعة: ثبتوا القرارات ثم ابنوا وأطلقوا النسخة النصية بعد اختبارها، دون انتظار الصوت. بعد ذلك، وبموافقة منفصلة، نفذوا الرسائل الصوتية غير الفورية في Object Storage مع سياسة احتفاظ وتكلفة مختبرة. ادرسوا المكالمات الحية كمرحلة مستقلة لاحقة، ولا توسعوا البنية إلى خدمات مستقلة قبل وجود حاجة مثبتة.

هذا المستند تصميم تنفيذي وليس تنفيذًا. لا يتضمن اختيار مزود ذكاء اصطناعي أو صوت، ولا يثبت حدود استخدام قبل قياس التكلفة، ولا يفعّل الدفع.
